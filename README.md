## Featured Work

### AutoPipeline-AD

**Automated multi-objective anomaly detection for IoT and edge devices**

My MSc research focused on building an automated framework for evaluating anomaly-detection pipelines while considering both **model performance and deployment constraints**.

The central idea:

> The most accurate model is not necessarily the best model for a constrained device.

The framework explores candidate models, optimisation and hardware-aware evaluation to produce deployment-oriented rankings.

### Pipeline

```text
Dataset
   │
   ▼
Configuration
   │
   ▼
Label-aware Dataset Routing
   │
   ├───────────────┐
   ▼               ▼
Supervised      Unsupervised
Models          Models
   │               │
   └───────┬───────┘
           ▼
    Candidate Training
           │
           ▼
 Hyperparameter Optimisation
         Optuna
           │
           ▼
 Threshold Calibration
           │
           ▼
 Hardware-aware Evaluation
           │
           ▼
 Deployment-aware Ranking
```

### Models explored

`Decision Trees` · `Random Forest`
`Local Outlier Factor` · `Isolation Forest`

### Datasets

`SKAB` · `CIC-IDS`

### Key considerations

* Supervised, unsupervised and semi-supervised routing
* Automated hyperparameter search
* Optional threshold calibration
* Balanced model evaluation
* Memory-aware evaluation
* Deployment-oriented model ranking
* Prevention of evaluation-label leakage into unsupervised training

### Research direction

The broader goal is to move from:

```text
"Which model is most accurate?"
```

towards:

```text
"Which model provides the best trade-off
between performance and deployment constraints?"
```

### Cloud & Data Processing

Worked on an enterprise food-order processing workflow involving **AWS S3, Lambda and backend systems**.

A recurring data-quality issue involved missing or inconsistent product tags.

Rather than repeatedly correcting invalid data downstream, I proposed introducing a **middleware validation layer** to detect and handle invalid data before it propagated through the system.

The resulting workflow separated responsibilities across:

```text
Data Input
    ↓
Validation
    ↓
Backend Processing
    ↓
Automated Tests
    ↓
AWS Pipeline
    ↓
Monitoring
```

This gave me practical experience with the difference between solving a bug and **designing a system that prevents the bug from becoming a recurring production problem**.

## Engineering Philosophy

I like simple ideas that survive contact with reality.

A model with excellent benchmark performance isn't particularly useful if it cannot run within the constraints of the environment where it needs to operate.

Likewise, software isn't finished because it compiles.

It needs to be:

```text
Correct
  +
Maintainable
  +
Observable
  +
Deployable
  +
Useful
```

That's the engineering problem I enjoy solving.
